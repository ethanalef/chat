# Q&A

## How do we determine there are 4 services from this project's codebase/file structure?

### Answer

There are multiple indicators in the codebase that reveal the 4-service architecture:

### **1. Directory Structure in `cmd/`** (Most Obvious Indicator)

Each subdirectory under `cmd/` with a `main.go` represents a separate executable service:

```bash
$ find cmd -name "main.go" -type f
cmd/api/chat-api/main.go     ← Service 1: Chat REST API
cmd/api/admin-api/main.go    ← Service 2: Admin REST API
cmd/rpc/admin-rpc/main.go    ← Service 3: Admin gRPC Service
cmd/rpc/chat-rpc/main.go     ← Service 4: Chat gRPC Service
```

In Go projects, each `main.go` file compiles to a separate binary/executable service.

### **2. Build Configuration** (Definitive Source)

The `start-config.yml` explicitly declares all services:

```yaml
serviceBinaries:
  chat-api: 1      # REST API for chat users
  chat-rpc: 1      # gRPC backend for chat
  admin-api: 1     # REST API for admins
  admin-rpc: 1     # gRPC backend for admin ops
```

This tells the build system (`mage`) to compile and manage 4 separate services.

### **3. Implementation Structure**

The `internal/` directory has separate implementations for each service:

```
internal/
├── api/
│   ├── chat/      ← Implements chat-api handlers
│   └── admin/     ← Implements admin-api handlers
└── rpc/
    ├── chat/      ← Implements chat-rpc business logic
    └── admin/     ← Implements admin-rpc business logic
```

### **4. Configuration Files**

Each service has configuration files in the `config/` directory:

```bash
$ ls config/ | grep -E "chat-api|chat-rpc"
chat-api-admin.yml
chat-api-chat.yml
chat-rpc-admin.yml
chat-rpc-chat.yml
```

### Key Takeaway

The **clearest indicators** are:

1. **4 `main.go` files** in `cmd/` = 4 separate executables
2. **`start-config.yml`** explicitly lists: `chat-api`, `chat-rpc`, `admin-api`, `admin-rpc`

This follows a common microservices pattern where:
- **API services** (chat-api, admin-api) handle HTTP/REST requests from clients
- **RPC services** (chat-rpc, admin-rpc) handle gRPC calls and business logic
- API services call RPC services, which then access databases

The architecture follows this flow:
```
Client → API Service (Gin/HTTP) → RPC Service (gRPC) → Database (MongoDB/Redis)
```
